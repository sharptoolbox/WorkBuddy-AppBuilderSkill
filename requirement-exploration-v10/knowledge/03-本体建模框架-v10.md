# 本体驱动的软件建模方案

**Ontology-Driven Software Modeling Framework（单体同步版）**

> 完整建模规范 · 八大模型元文件 · 实施指南  
> 版本 10.0 | 2026年9月
>
> 本规范面向**单体同步部署的中小型业务系统**（如销售合同执行管理系统），  
> 跨对象协作一律由 M2 `syncTriggers` 同步编排与 M4/M6 流程承载，全部处理在同一事务边界内顺序完成。
>
> V10.0 相对 v9.0 的变更要点：
>
> 1. **恢复 M4 场景模型**：以"业务场景"为单位承载端到端业务流程的业务语义（业务目标、起止条件、业务阶段与责任角色、结束触发规则），与 M6 流程模型形成"业务语义层 + 可执行编排层"的两层表达，模型总数由七个增为八个；
> 2. **M5 主体模型权限细化**：权限目标类型由「行为 / 实体」两级扩为「菜单 / 屏幕 / 操作功能点 / 行为 / 实体」五类，明确菜单可见性与按钮可用性的分配规则、权限组、多角色并集与显式拒绝优先级、系统角色的权限边界；
> 3. **MU UI 模型元素说明结构化**：每个界面元素逐项给出十项关键属性（字段项、控件 ID、对应对象属性、控件类型、数据来源类型、数据源、默认值、可编辑、必填、对应行为），并新增界面区块、依赖对象与 CUD 操作、授权角色、界面初始化规则、界面事件联动规则；
> 4. **统一跨对象协作语义**：跨对象联动只由 M2 `syncTriggers`（条件判断引用 M3 规则）与 M4/M6 流程承载，全部处理在同一事务边界内同步完成；规则一律被行为同步调用，本规范不引入异步消息、订阅式联动或消息中间件相关的建模要求。

# 第一章  方案概述与设计哲学

## 1.1  框架定位

本方案面向具有明确领域边界、**采用单体同步部署**的中小型业务软件，以"本体"（Ontology）作为系统设计的核心隐喻，将业务世界中的"存在（What）"、"行为（How）"、"规则（Why）"、"场景与流程（Journey）"、"主体权限（Who）"、"查询表达（Read/Report）"和"界面入口（UI）"分离建模，并通过**同步流程编排**实现跨对象协作。

跨对象联动由"行为完成后同步调用下游行为（经规则判断）"承载；端到端业务由 M4 场景模型表达业务语义、由 M6 流程模型表达可执行编排。全部处理在同一事务边界内顺序完成，符合单体系统的简单性与可调试性要求。

与传统需求分析方法（如 UML 用例图、功能规格说明书）相比，本框架具有以下核心差异：

- **语义驱动**：模型元素具有明确的业务语义，而非纯粹的技术描述；
- **正交分解**：对象、行为、规则、场景、主体、流程、查询报表和界面各自承担单一职责，可独立演进；
- **同步编排**：跨对象协作通过流程编排或行为后置同步调用完成，链路顺序、可预测、可调试；
- **场景与编排分离**：端到端业务场景（M4）与流程编排（M6）分离建模，前者回答"业务怎么走、谁负责"，后者回答"流程实例如何推进"；审批流独立成 M6 `APPROVAL` 流程，不与行为内部逻辑混合；
- **读写分离**：跨对象查询、统计和固定报表独立建模，不把复杂查询结构塞入原子行为或业务规则；
- **权限分层**：菜单可见性、屏幕进入、按钮可用性、行为授权四级权限统一在主体模型定义，界面只负责渲染结果；
- **可追溯性**：每个实现单元都可以溯源到具体的本体模型定义。

## 1.2  八大模型元文件总览

| 编号     | 模型名称                           | 核心职责                                                          |
| ------ | ------------------------------ | ------------------------------------------------------------- |
| **M1** | 对象模型 Object Model              | 定义数据实体、实体属性、实体间的双向关联与参照完整性约束                                  |
| **M2** | 行为模型 Behavior Model            | 定义对象的原子行为方法、触发条件、前置后置约束及同步联动（syncTriggers）                    |
| **M3** | 规则模型 Rule Model                | 定义跨对象、跨行为或需要独立复用的业务决策规则（被同步调用）                                |
| **M4** | 场景模型 Scenario Model            | 定义端到端业务场景的业务语义：业务目标、起止条件、业务阶段与阶段步骤、责任角色、涉及对象、结束触发规则           |
| **M5** | 主体模型 Actor Model               | 定义系统参与者、角色、四级权限目标（菜单 / 屏幕 / 操作功能点 / 行为）及权限分配关系                |
| **M6** | 流程模型 Flow Model                | 定义端到端业务协同流和审批流的可执行编排：活动节点、网关、分支、子流程调用与审批结果                    |
| **M7** | 查询统计与报表模型 Query & Report Model | 定义跨对象查询、统计分析和固定业务报表的来源、关联、条件、结果列、聚合及可选参考 SQL                  |
| **MU** | UI 模型 UI Model                 | 定义总体界面、菜单层级、屏幕（区块 + ASCII 布局 + 界面元素十项关键属性）、操作功能点及其与行为、权限的对应关系 |

> 说明：模型编号沿用历史体系（M1～M7、MU），编号顺序即建模顺序推荐顺序。M4 场景模型通过 `flowRefs` 引用 M6 流程，引用方向为 M4 → M6，M6 不反向引用 M4。


## 1.3  模型间关系全景

八个模型之间的依赖与引用关系如下：

```
M4 场景模型      依赖   M1 对象模型 + M6 流程模型（flowRefs）+ M5 角色模型 + M2 行为 + M3 规则
M6 流程模型      依赖   M1 对象模型 + M2 行为模型 + M3 规则模型 + M5 角色模型
M7 查询报表模型  依赖   M1 对象模型 + M2 查询行为（一对一绑定）
M2 行为模型      依赖   M1 对象模型 + M3 规则模型 + M5 主体模型（+ syncTriggers 同步联动）
M3 规则模型      引用   M1 对象模型（只读）
M5 主体模型      引用   M1 对象模型 + M2 行为模型（行为授权）+ MU 菜单与功能点（可见性授权）
MU UI 模型      依赖   M1 对象模型 + M2 行为模型 + M5 权限（渲染依据）+ M6 流程模型 + M7 查询报表模型
```

**关键设计决策**：

1. M2 行为保持原子性：一个行为只操作一个对象，产生确定性的状态变更；跨对象联动通过 `syncTriggers` 同步调用下游行为。
2. `syncTriggers` 中的条件判断必须引用 M3 规则，规则只判断、不直接修改对象状态；对象状态变化始终由行为完成。
3. M4 场景模型只描述端到端业务的业务语义（阶段、责任、对象、起止条件、结束触发规则），不定义活动节点、网关、分支与审批结果；可执行编排归 M6。
4. M6 统一承载端到端协同流与审批流的编排。人工活动只能通过 `roleRef` 引用 M5 中的 `roleId`，不得直接引用具体人员或填写自由文本参与人。
5. M6 可以调用 M2 行为、M3 规则及其他 M6 子流程，但不得复制这些模型中的定义。
6. M7 只与 M1、M2 发生直接关系。M7 定义查询内容，M2 定义执行该查询报表对象的原子行为，两者严格一对一；M7 不直接引用 M3、M5 或 M6。
7. M5 是权限的唯一权威：菜单可见性、屏幕进入、操作功能点可用性、行为执行授权全部在主体模型中定义并分配；MU 只通过 `permissionRef` 引用，不自行定义权限或角色。
8. MU 是入口层/追溯层：只通过稳定 ID 引用 M1～M7，不重新定义这些模型的任何语义；MU 的操作功能点（actionPoint）是"一次用户操作 → 调用 M2 行为"的唯一界面入口，并必须绑定一个 M5 操作功能点权限。
9. **可追溯门禁**：M2 中 `triggerType=USER_ACTION` 的行为必须被至少一个 MU 操作功能点引用；MU 操作功能点引用的行为必须存在（反向可追溯、正向一致）。

## 1.4  同步联动的标准语义

跨对象联动在本框架中的标准表达如下：

**无条件联动（直接同步调用）**：

```text
源对象行为
-> 成功后同步调用下游行为（无额外条件）
-> 目标对象行为
```

**有条件联动（规则介入）**：

```text
源对象行为
-> 成功后同步调用 M3 规则判断
-> 规则满足：同步调用目标行为；规则不满足：不执行目标行为
-> 目标对象行为
```

> 强制语义边界：行为只回答"做什么并改变什么状态"；规则只回答"条件是否满足"；行为之间的联动关系由 `syncTriggers` 显式声明。禁止把"全部收齐时关闭合同"这类条件结论写进源行为本身，必须拆为"M3 关闭校验规则 + 目标关闭行为"。
>
> 三类联动互不越界：**界面事件联动**（MU `linkageRules`）只在界面前端完成，不修改任何对象状态；**跨对象联动**由 M2 `syncTriggers` + M3 规则承载；**流程启动**由 M6 的 `trigger.behaviorRef` 承载。

# 第二章  M1 对象模型

## 2.1  设计目标与领域建模原则

对象模型是整个本体体系的基础，负责描述业务域中的核心领域对象及其关系，对应领域驱动设计（DDD）中的领域模型层。其核心设计原则是：

- **业务完整性优先**：从业务视角建模，而非数据库表结构视角；
- **聚合边界清晰**：通过聚合根（Aggregate Root）保证业务不变性；
- **实现延迟绑定**：对象模型关注业务语义，数据库表拆分在实现阶段决策。

> **关键设计理念**：对象模型描述的是"业务对象"而非"数据库表"。例如，合同（包含合同头和付款条款明细）在业务层面是一个完整的聚合，不应拆分为两个独立实体建模。数据库层面的表拆分是持久化实现阶段的技术决策，由实现阶段的 ORM 注解或 DDL 直接落地，本框架不为其建立独立模型。

## 2.2  领域对象分类体系

| 对象类型                    | 说明                             | 标识特征      | 生命周期           |
| ----------------------- | ------------------------------ | --------- | -------------- |
| **聚合根（Aggregate Root）** | 业务完整性的边界，对外暴露的唯一入口，包含子实体和值对象   | 有全局唯一标识   | 有独立生命周期，可独立存在  |
| **实体（Entity）**          | 聚合内部的子对象，有标识但不能脱离聚合根独立存在       | 有聚合内唯一标识  | 依赖聚合根生命周期，级联删除 |
| **值对象（Value Object）**   | 无标识的不可变对象，通过属性值判断相等性，描述聚合的某个特征 | 无标识，通过值相等 | 依附于聚合根或实体，不可变  |

### 2.2.1  聚合根设计原则

1. **唯一入口原则**：外部只能通过聚合根访问聚合内部对象，不能直接操作子实体；
2. **事务边界原则**：一个事务只修改一个聚合根，跨聚合通过同步联动（syncTriggers）或流程编排完成；
3. **不变性保护**：聚合根负责维护聚合内的业务不变性约束；
4. **引用原则**：聚合之间通过 ID 引用，而非对象引用，避免聚合边界模糊。

### 2.2.2  聚合识别指南

| 判断维度  | 聚合内（同一聚合）    | 聚合间（独立聚合） |
| ----- | ------------ | --------- |
| 业务完整性 | 必须同时存在才有业务意义 | 可以独立存在    |
| 生命周期  | 同生共死，级联删除    | 独立生命周期    |
| 事务边界  | 必须在同一事务中修改   | 可在不同事务中修改 |
| 访问路径  | 只能通过聚合根访问    | 可以直接访问    |
| 引用方式  | 对象引用（组合/聚合）  | ID 引用（关联） |

**示例**：

- ✅ 合同 + 付款条款 → 同一聚合（合同是聚合根，条款是子实体）；
- ✅ 合同 + 开票明细 → 独立聚合（开票有独立生命周期，通过合同 ID 关联）；
- ❌ 合同 + 客户 → 独立聚合（通过客户 ID 关联，而非组合）；
- ❌ 合同 + 产品 → 独立聚合（产品有独立生命周期）。

### 2.3.4  属性（Attribute）

| 属性名             | 类型                | 说明                                                                                                                        |
| --------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------- |
| name            | String            | 属性名（英文 camelCase）                                                                                                         |
| label           | String            | 业务展示名（中文）                                                                                                                 |
| type            | DataType          | 类型：String / Integer / Decimal / Date / DateTime / Boolean / Enum / Money / ValueObject / AggregateRootRef / DictionaryRef |
| required        | Boolean           | 是否必填                                                                                                                      |
| unique          | Boolean           | 是否唯一（仅对聚合根属性有效）                                                                                                           |
| defaultValue    | Any               | 默认值                                                                                                                       |
| enumValues      | String[]          | 当 type=Enum 时的枚举值列表                                                                                                       |
| valueObjectRef  | String            | 当 type=ValueObject 时引用的值对象名称                                                                                              |
| targetAggregate | AggregateRef      | 当 type=AggregateRootRef 时必填，指向被引用聚合根的 ID                                                                                  |
| dictionaryRef   | DictionaryTypeRef | 当 type=DictionaryRef 时必填，包含 dictionaryId 和 typeCode                                                                       |
| refRules        | AttributeRule[]   | 可选；只依赖当前属性值、可在该属性内部完整定义的扩展规则                                                                                              |

`AggregateRootRef` 表示"存储另一个聚合根 ID 的标量属性"，而不是内嵌对象或数据库外键对象。该类型在代码生成时仍可映射为目标聚合根 ID 的实际标量类型，但在本体层必须通过 `targetAggregate` 显式声明目标。**在 MU UI 模型（§9）中，AggregateRootRef 属性显示为"跳选框"控件。**

`DictionaryRef` 表示属性值来自 M1 对象模型中的数据字典类型。业务数据保存字典项稳定的 `code`，界面显示 `label`。`DictionaryRef` 不得同时声明 `enumValues`。**在 MU UI 模型中，DictionaryRef 与 Enum 属性显示为"下拉列表框"控件。**

#### 属性扩展规则（AttributeRule / refRules）

`refRules` 用于定义只依赖当前属性值即可判断的局部规则。此类规则属于 M1 对象模型，不得重复放入 M3 规则模型。

| 属性名              | 类型     | 说明                                         |
| ---------------- | ------ | ------------------------------------------ |
| name             | String | 属性规则名称，在当前属性内唯一                            |
| description      | String | 规则业务说明                                     |
| expression       | String | 属性规则表达式，使用 `value` 表示当前属性值                 |
| violationMessage | String | 规则不满足时返回的业务提示                              |
| enforcedAt       | Enum   | ON_CREATE / ON_UPDATE / ON_DELETE / ALWAYS |

属性规则分层原则：

1. 可以用内置字段表达的约束，优先使用内置字段（如 `required`、`unique`），不重复写入 `refRules`；
2. 无法由内置字段表达、但只依赖当前属性值的规则使用 `refRules`（如金额必须大于 0）；
3. 依赖同一对象多个属性或聚合内部子实体的规则使用聚合 `invariants`（如付款比例合计等于 100%）；
4. 依赖其他独立对象、多个行为结果或需要被多个行为复用的规则，进入 M3 规则模型。

### 2.3.5  数据字典（Data Dictionary）

数据字典是对象模型中的引用数据定义，不是值对象、聚合根或运行时业务实体。同一个数据字典对象可以维护多个平级字典类型。

#### 字典类型

| 属性名         | 类型               | 说明                   |
| ----------- | ---------------- | -------------------- |
| typeCode    | String           | 数据字典对象内唯一的稳定编码       |
| typeName    | String           | 中文显示名称               |
| description | String           | 可选说明                 |
| items       | DictionaryItem[] | 平级字典项，不允许 parentCode |

#### 字典项

| 属性名       | 类型      | 说明                     |
| --------- | ------- | ---------------------- |
| code      | String  | 类型内唯一的稳定业务存储值          |
| label     | String  | 界面显示文本，可修改但不影响已有业务数据   |
| enabled   | Boolean | 是否可被新增数据选择；已使用项应停用而非删除 |
| sortOrder | Integer | 显示顺序                   |

#### 字典引用约束

- `dictionaryRef.dictionaryId` 必须指向存在的数据字典对象；
- `dictionaryRef.typeCode` 必须指向该对象内存在的字典类型；
- 数据字典项当前为平级结构，规范中不定义 `parentCode` 或其他层级字段。

### 2.3.6  聚合不变性约束（Invariant）

| 属性名              | 类型     | 说明                                         |
| ---------------- | ------ | ------------------------------------------ |
| name             | String | 约束名称                                       |
| expression       | String | 约束表达式，可跨聚合内的子实体和值对象                        |
| violationMessage | String | 违反约束时的业务错误消息                               |
| enforcedAt       | Enum   | ON_CREATE / ON_UPDATE / ON_DELETE / ALWAYS |

### 2.3.7  聚合间关联（Aggregate Association）

聚合之间通过 ID 引用建立关联：

| 属性名             | 类型           | 说明                                                    |
| --------------- | ------------ | ----------------------------------------------------- |

| sourceAggregate | AggregateRef | 来源聚合根                                                 |
| targetAggregate | AggregateRef | 目标聚合根                                                 |
| associationType | Enum         | REFERENCE（引用）/ DEPENDENCY（依赖）                         |
| sourceRole      | String       | 来源端角色名                                                |
| targetRole      | String       | 目标端角色名                                                |
| cardinality     | Enum         | ONE_TO_ONE / ONE_TO_MANY / MANY_TO_ONE / MANY_TO_MANY |
| referenceField  | String       | 存储目标聚合根 ID 的字段名                                       |

## 2.5  聚合建模最佳实践

### 2.5.1  聚合大小控制

- **小聚合优先**：聚合越小，并发冲突越少，性能越好；
- **业务完整性优先**：不能为了性能牺牲业务完整性；
- **经验法则**：一个聚合包含的子实体不超过 3-5 个，总字段数不超过 30 个。

### 2.5.2  聚合拆分时机

| 拆分信号          | 处理方式                |
| ------------- | ------------------- |
| 子实体有独立生命周期    | 提升为独立聚合根，通过 ID 引用   |
| 子实体被多个聚合引用    | 提升为独立聚合根            |
| 聚合内部分字段很少一起修改 | 拆分为多个聚合，通过同步联动保持一致性 |

### 2.5.3  数据冗余策略

为避免跨聚合查询，可在聚合内冗余其他聚合的关键展示信息（如名称、编码），通过同步联动保持最终一致。只冗余展示用的稳定字段，不冗余频繁变化的字段。

### 2.5.4  聚合根 ID 设计

| ID 类型 | 适用场景           | 示例                |
| ----- | -------------- | ----------------- |
| UUID  | 分布式系统，客户端生成 ID | `550e8400-...`    |
| 业务编号  | 有业务规则的编号体系     | `HT-2026-08-0001` |
| 自增 ID | 单库自增主键         | `10001`           |

# 第三章  M2 行为模型

## 3.1  设计目标

行为模型定义对象能够执行的原子行为方法。每个行为是单一对象发出的、不可再分的核心操作单元。复杂判断通过规则模型注入；跨对象联动通过 `syncTriggers` 同步调用下游行为；端到端和审批流转通过 M6 流程编排。

> **关键设计原则**：行为模型的核心约束是"原子性"——每个行为方法只做一件事，操作一个对象，产生确定性的状态变更。跨对象的联动关系必须通过 `syncTriggers` 显式声明，不得在行为方法内部隐含地直接操作其他聚合。

## 3.2  模型元素规范

### 3.2.1  行为（Behavior）

| 属性名                 | 类型              | 说明                                                                |
| ------------------- | --------------- | ----------------------------------------------------------------- |
| id                  | String          | 行为唯一标识，建议格式：{EntityAlias}_{ActionName}                            |
| name                | String          | 行为业务名称（中文动宾短语）                                                    |
| ownerEntity         | EntityRef       | 行为所属对象                                                            |
| behaviorType        | Enum            | COMMAND（指令，改变状态）/ QUERY（查询，只读）                                    |
| triggerType         | Enum            | USER_ACTION（用户触发）/ SYSTEM（系统自动）                                   |
| preconditions       | Condition[]     | 前置条件集合，全部满足才可执行                                                   |
| postconditions      | StateChange[]   | 执行后的状态变更描述                                                        |
| appliedRules        | RuleRef[]       | 调用的规则模型引用                                                         |
| requiredPermissions | PermissionRef[] | 执行所需权限（引用 M5 主体模型）                                                |
| syncTriggers        | SyncTrigger[]   | 执行成功后同步调用的下游行为（跨对象联动）                                             |
| queryReportRef      | QueryReportRef  | 当 behaviorType=QUERY 且行为执行 M7 查询统计或报表对象时填写；与 M7.behaviorRef 严格一对一 |

### 3.2.2  同步联动（SyncTrigger）

`syncTriggers` 是跨对象联动的唯一载体。行为执行成功后，按顺序同步执行 `syncTriggers` 中声明的联动：

| 属性名         | 类型          | 说明                             |
| ----------- | ----------- | ------------------------------ |
| ruleRef     | RuleRef     | 可选；条件判断规则引用。填写时表示"规则满足才触发下游行为" |
| behaviorRef | BehaviorRef | 必填；满足条件（或无额外条件）时同步调用的下游行为      |
| description | String      | 联动业务说明                         |

约束：

1. `ruleRef` 省略表示无条件联动，下游行为直接同步调用；
2. `ruleRef` 填写时必须引用 M3 规则，规则只判断条件，不修改状态；
3. 同一行为可声明多条 `syncTriggers`，按声明顺序执行；
4. 下游行为必须作用于另一个独立聚合（跨对象），同一聚合内部变化不得用 `syncTriggers` 表达；
5. 联动失败（规则不满足或下游行为异常）的语义必须在行为的 `postconditions` 或 M6 流程中明确，禁止隐含吞掉异常。

### 3.2.3  前置/后置条件（Condition / StateChange）

使用简洁的谓词表达式语法：

- 前置条件示例：`contract.status == '待审批'  AND  contract.totalAmount > 0`
- 状态变更示例：`contract.status = '已生效'  |  contract.activateAt = NOW()`
- 支持跨实体引用：`invoice.receivedAmount <= invoice.invoiceAmount`

## 3.4  一致性约束

1. `triggerType=USER_ACTION` 的行为必须被至少一个 MU 操作功能点引用（可追溯性门禁，防止孤儿行为）；
2. `syncTriggers` 中引用的 `behaviorRef`、`ruleRef` 必须分别存在于 M2、M3；
3. `syncTriggers` 的下游行为必须操作另一个独立聚合（跨对象），禁止同聚合内自我联动；
4. 行为 `postconditions` 描述的状态变更，应与 MU 操作功能点的回显/刷新行为衔接（如保存成功后刷新列表）；
5. `queryReportRef` 只出现在 `behaviorType=QUERY` 的行为上，并与 M7 `behaviorRef` 双向一致、严格一对一。

# 第四章  M3 规则模型

## 4.1  设计目标与边界

规则模型专注于跨对象、跨行为或需要独立复用的解耦业务规则，是从对象局部约束和行为逻辑中分离出来的独立关切。其核心价值在于：同一规则可以被多个行为引用，规则变更不影响对象结构和行为定义。

> **重要边界说明**：能够在单个属性内部定义清楚的规则不进入 M3。必填、唯一、类型、枚举和数据字典约束直接使用 M1 属性字段；只依赖当前属性值的扩展表达式使用属性 `refRules`；依赖同一对象多个属性或聚合内部子实体的规则使用聚合 `invariants`。M3 只处理超出单个对象内部边界的业务判断、计算、推导，并且**一律由行为同步调用**。

### 4.1.1  M1 局部规则与 M3 规则的判定

| 规则特征               | 归属位置                    | 示例                 |
| ------------------ | ----------------------- | ------------------ |
| 属性内置约束             | M1 Attribute 字段         | 必填、唯一、枚举、字典引用      |
| 只读取当前属性值           | M1 Attribute.refRules   | 金额大于 0、名称长度不超过 100 |
| 读取同一对象多个属性或聚合内部子实体 | M1 Aggregate.invariants | 付款比例合计等于 100%      |
| 读取两个或多个独立对象        | M3 Rule                 | 累计收款金额达到合同总金额      |
| 依赖行为执行结果或被多个行为复用   | M3 Rule                 | 合同关闭资格校验、阶段开票上限校验  |
| 调用外部规则引擎或外部数据决策    | M3 Rule                 | 信用风险评分、合规名单校验      |

判断顺序：

```text
内置字段能表达？
-> 是：使用属性内置字段
-> 否：是否只依赖当前属性值？
   -> 是：使用 Attribute.refRules
   -> 否：是否只依赖同一聚合内部数据？
      -> 是：使用 Aggregate.invariants
      -> 否：进入 M3 规则模型（被行为同步调用）
```

## 4.2  规则分类体系

| 规则类型                      | 说明                                     | 触发方式  |
| ------------------------- | -------------------------------------- | ----- |
| 验证规则（Validation Rule）     | 对跨属性、跨对象或行为上下文执行验证，返回 true/false，不改变状态 | 被行为调用 |
| 计算规则（Calculation Rule）    | 根据输入参数计算并返回结果值                         | 被行为调用 |
| 推导规则（Derivation Rule）     | 基于已知属性推导出其他属性值                         | 被行为调用 |
| 转换规则（Transformation Rule） | 将一种数据格式转换为另一种                          | 被行为调用 |
| 风控规则（Risk Rule）           | 评估业务风险，返回风险等级或通过/拒绝决策                  | 被行为调用 |

> 所有规则均是被行为（或经 `syncTriggers`）同步调用的被动组件，不主动触发任何行为。规则只负责判断与计算，对象状态变化始终由行为完成。

## 4.3  模型元素规范

### 4.3.1  通用规则属性

| 属性名            | 类型            | 说明                                                            |
| -------------- | ------------- | ------------------------------------------------------------- |
| id             | String        | 规则唯一标识，建议格式：RULE-{Domain}-{Seq}                               |
| name           | String        | 规则业务名称                                                        |
| ruleType       | Enum          | VALIDATION / CALCULATION / DERIVATION / TRANSFORMATION / RISK |
| description    | String        | 规则的业务逻辑说明                                                     |
| inputParams    | Param[]       | 输入参数定义（名称、类型、来源字段）                                            |
| outputType     | DataType      | 返回值类型，通常为 Boolean 或结构化结果                                      |
| expression     | String        | 规则表达式（支持伪代码或 DSL，不限定具体语言）                                     |
| reusedBy       | BehaviorRef[] | 引用本规则的行为列表（反向追踪）                                              |
| externalEngine | String        | 若委托外部规则引擎，填写引擎名称（可选）                                          |
| version        | String        | 规则版本，支持规则的独立版本管理                                              |

### 4.3.2  输入参数（Param）

| 属性名         | 类型       | 说明                              |
| ----------- | -------- | ------------------------------- |
| name        | String   | 参数名称                            |
| type        | DataType | 参数类型                            |
| sourceField | String   | 来源字段路径，如 "contract.totalAmount" |
| required    | Boolean  | 是否必填                            |
| description | String   | 参数说明                            |


## 4.4  YAML 元文件模板

```yaml
# M3 规则模型元文件 - m3-rule-model.yaml
model_type: RULE
version: "2.0"
domain: "销售合同执行管理"

rules:
  - id: RULE-CONTRACT-CLOSE-CHECK
    name: 合同关闭资格校验
    ruleType: VALIDATION
    description: 判断合同累计收款金额是否已达到合同总金额，达到则可关闭
    inputParams:
      - name: contractId
        type: String
        sourceField: Contract.contractId
        required: true
      - name: totalAmount
        type: Decimal
        sourceField: Contract.totalAmount
        required: true
      - name: receivedAmount
        type: Decimal
        sourceField: Receipt.aggregatedAmount
        required: true
    outputType: Boolean
    expression: |
      receivedAmount >= totalAmount
    reusedBy:
      - Receipt_Record          # 通过 syncTriggers 引用
    version: "1.0"

  - id: RULE-INVOICE-AMOUNT-CHECK
    name: 阶段开票金额上限校验
    ruleType: VALIDATION
    description: 校验某付款阶段累计开票金额不超过该阶段应开票金额
    inputParams:
      - name: stageAmount
        type: Decimal
        sourceField: PaymentStage.amount
        required: true
      - name: invoicedAmount
        type: Decimal
        sourceField: Invoice.aggregatedAmount
        required: true
    outputType: Boolean
    expression: |
      invoicedAmount <= stageAmount
    reusedBy:
      - Invoice_Issue
    version: "1.0"
```

## 4.5  最佳实践

- **单一职责**：一个规则只判断一个业务条件；
- **明确输入输出**：清晰定义输入参数和输出结果；
- **无副作用**：规则只判断/计算，不改变任何对象状态；
- **规则失败不阻断其他处理**：规则校验失败应返回明确业务提示，由调用方（行为）决定后续处理；
- **版本管理**：规则升级时保持输入输出接口兼容，支持独立版本管理与回滚。

# 第五章  M4 场景模型

## 5.1  设计目标与边界

M4 场景模型以**业务场景**为单位，描述端到端业务流程的业务语义：一个业务目标在什么条件下开始、经过哪些业务阶段、每个阶段由谁负责、操作与读取哪些业务对象、到什么条件结束，以及流程走到结束后是否需要触发规则处理。

同一份端到端业务在框架中被表达两次，两层职责互不重叠：

- **M4 场景模型（业务语义层）**&#x56DE;答"这条端到端业务怎么走、谁在走、碰哪些对象、何时算结束"；
- **M6 流程模型（可执行编排层）**&#x56DE;答"流程实例如何从开始推进到结束：活动节点、网关、分支、子流程调用、审批结果"。

> **强制边界**：M4 只引用、不重定义。场景不定义对象、属性、行为、规则、角色、权限和界面元素，这些分别由 M1/M2/M3/M5/MU 承载；M4 也不定义活动节点、网关、分支、审批结果与超时约束——这些是 M6 的职责。

**标准语义链**：

```text
M2 行为（用户触发或系统触发）
-> 达到场景的启动条件 startCondition
-> 场景按业务阶段顺序推进
   （阶段步骤引用 M2 行为 / M6 流程 / M3 规则，声明责任角色与操作对象）
-> 达到场景的结束条件 endCondition
-> 结束触发规则落地（是否写审批记录、是否触发下游行为、是否声明跨对象联动）
```

> 不是每个功能都需要建立场景。单对象的增删改查、纯查询与报表、单一审批动作都不属于 M4；只有**跨业务阶段、跨对象、有明确业务目标**的端到端业务才建立场景。项目可以只有一个场景，不得为了满足数量要求虚构场景。

## 5.2  场景与流程的职责分界

| 判断问题      | M4 场景模型                                                 | M6 流程模型                                                  |
| --------- | ------------------------------------------------------- | -------------------------------------------------------- |
| 核心目的      | 描述端到端业务场景的业务语义与阶段划分                                     | 描述流程实例如何从开始推进到结束                                         |
| 主要元素      | 场景、业务阶段、阶段步骤、结束触发规则                                     | 流程、活动节点、网关、分支、子流程调用                                      |
| 业务目标与起止条件 | 由 `businessGoal` / `startCondition` / `endCondition` 定义 | 由流程 `preconditions` / `postconditions` 定义                |
| 责任与参与者    | 阶段级 `roleRef`（谁负责这个阶段）                                  | 活动级 `roleRef`（谁处理这个任务），必须属于流程 `roleRefs`                 |
| 审批节点与审批结果 | 不定义                                                     | 由 `APPROVAL` 流程的 `APPROVAL_TASK` + `approvalOutcomes` 承载 |
| 网关与分支     | 不定义                                                     | 由 `GATEWAY` + `FlowBranch` 承载                            |
| 阶段可循环     | 由 `nextStages` 指向自身表达（如"多次开票、多笔收款"）                     | 由流程中的回边或循环活动表达                                           |
| 引用方向      | M4 通过 `flowRefs` / `stage.flowRef` 引用 M6                | M6 不反向引用 M4                                              |
| 版本管理      | 场景独立版本                                                  | 流程独立版本                                                   |

**组合关系（强制）**：同一个业务场景通常对应一条 M6 `COLLABORATION` 协同流；场景的业务阶段在协同流中展开为活动节点与网关。审批子流程只出现在 M6，M4 在其阶段步骤中用 `FLOW_CALL` 引用该子流程，而不复制其节点定义。

## 5.3  模型元素规范

### 5.3.1  场景（Scenario）

| 属性名                | 类型                | 说明                                          |
| ------------------ | ----------------- | ------------------------------------------- |
| scenarioId         | String            | 场景唯一标识，建议格式 `SCN-{DOMAIN}-{NNN}`            |
| name               | String            | 场景名称，如"合同全生命周期场景"                           |
| businessGoal       | String            | 业务目标：这条场景为什么存在、解决什么业务问题                     |
| description        | String            | 业务范围与边界说明；可标注本场景对应的业务单据编号范围                 |
| objectRefs         | AggregateRef[]    | 场景涉及的业务对象范围，引用 M1 聚合根                       |
| actorRefs          | RoleRef[]         | 场景涉及的执行角色集合，引用 M5 `roles.roleId`（含系统自动执行角色） |
| startCondition     | String            | 场景开始条件（业务可读描述，如"销售合同已完成线下签字盖章，具备登记条件"）      |
| endCondition       | String            | 场景结束条件（业务可读描述）                              |
| triggerBehaviorRef | BehaviorRef       | 场景启动触发器，引用 M2 行为（首次进入本场景的行为）                |
| flowRefs           | FlowRef[]         | 场景引用的 M6 流程集合（协同流与审批子流程）                    |
| stages             | ScenarioStage[]   | 业务阶段集合，按 `stageNo` 顺序推进                     |
| endRules           | ScenarioEndRule[] | 结束触发规则集合，覆盖正常结束 / 异常结束 / 提前结束               |
| version            | String            | 场景定义版本                                      |
|                    |                   |                                             |

### 5.3.2  业务阶段（ScenarioStage）

一个业务阶段对应端到端流程中的一个"环节"：一次明确的业务活动、一个执行角色、一批操作对象。

| 属性名         | 类型             | 说明                                                                                                              |
| ----------- | -------------- | --------------------------------------------------------------------------------------------------------------- |
| stageNo     | String         | 阶段序号，如 `01`、`02`；同一场景内唯一                                                                                        |
| name        | String         | 阶段名称（业务活动名），如"保存合同草稿"、"完成合同登记审批"                                                                                |
| stageType   | Enum           | `BEHAVIOR_CALL`（执行功能点 / 行为）/ `FLOW_CALL`（执行流程）/ `RULE_EVALUATE`（规则判定）/ `WAIT`（等待态，无状态变更）/ `SYSTEM_TASK`（系统自动执行） |
| behaviorRef | BehaviorRef    | `stageType=BEHAVIOR_CALL` 时必填；引用 M2 行为                                                                          |
| flowRef     | FlowRef        | `stageType=FLOW_CALL` 时必填；引用 M6 流程                                                                              |
| ruleRef     | RuleRef        | `stageType=RULE_EVALUATE` 时必填；引用 M3 规则                                                                          |
| objectRefs  | AggregateRef[] | 本阶段操作或读取的对象，引用 M1 聚合根                                                                                           |
| roleRef     | RoleRef        | 本阶段的执行角色，引用 M5 角色；系统自动执行时填写系统角色                                                                                 |
| refs        | Ref[]          | 本阶段涉及的不变量与规则编号清单（如 `INV-01`、`R-09`），用于需求可追溯                                                                     |
| steps       | ScenarioStep[] | 可选；本阶段内部的细化步骤，用于表达阶段内的顺序与判断                                                                                     |
| nextStages  | StageRef[]     | 后继阶段；指向自身表示该阶段可循环执行                                                                                             |
| isTerminal  | Boolean        | 是否为终止阶段（场景结束条件的达成处）；至少一个阶段为 `true`                                                                              |

### 5.3.3  阶段步骤（ScenarioStep）

阶段步骤是对业务阶段的细化，用于表达"一个阶段内还需要按顺序做几件事"。阶段本身已足以描述业务语义时，`steps` 可省略。

| 属性名         | 类型          | 说明                                                           |
| ----------- | ----------- | ------------------------------------------------------------ |
| stepNo      | String      | 步骤序号，阶段内唯一                                                   |
| name        | String      | 步骤名称                                                         |
| stepType    | Enum        | `BEHAVIOR_CALL` / `FLOW_CALL` / `RULE_EVALUATE` / `VALIDATE` |
| behaviorRef | BehaviorRef | 引用 M2 行为                                                     |
| flowRef     | FlowRef     | 引用 M6 流程                                                     |
| ruleRef     | RuleRef     | 引用 M3 规则                                                     |
| description | String      | 步骤说明（含判断口径）                                                  |
| nextSteps   | StepRef[]   | 后继步骤；为空表示阶段内最后一步                                             |

阶段步骤**不得**定义网关、人工任务、审批结果与角色分配。业务条件进入 M3 规则；分支与任务节点进入 M6。

### 5.3.4  结束触发规则（ScenarioEndRule）

结束触发规则回答"流程走到最后一个环节结束后，是否需要触发规则处理，以及触发何种规则 / 行为"。它对应审批流与协同流中"结束后的落地动作"，是需求侧最容易遗漏、实现侧最容易各自假设的地方，因此强制显式声明。

| 属性名                 | 类型            | 说明                                                                        |
| ------------------- | ------------- | ------------------------------------------------------------------------- |
| outcomeCode         | Enum          | 结束情形：`NORMAL_END`（正常结束：末阶段完成）/ `REJECTED`（异常结束：被驳回）/ `WITHDRAWN`（提前结束：撤回） |
| description         | String        | 该结束情形下系统应做什么（业务可读描述）                                                      |
| ruleRef             | RuleRef       | 可选；落地判定所引用的 M3 规则（如金额分级规则）                                                |
| behaviorRefs        | BehaviorRef[] | 可选；该结束情形下要执行的行为清单                                                         |
| syncTriggerDeclared | Boolean       | 是否触发跨对象联动；`true` 时必须与 M2 对应行为的 `syncTriggers` 非空一致                        |
| writeRecord         | Boolean       | 是否写入历史记录对象（如审批记录）；历史对象永久保留                                                |
| remark              | String        | 边界说明，如"本条不触发下游行为，等待重新提交"                                                  |

**约束**：`syncTriggerDeclared=true` 时，`behaviorRefs` 中至少一个行为的 `syncTriggers` 必须非空，且触发的下游行为必须与场景阶段中出现的阶段一致，禁止在场景里重新定义联动链。

## 5.5  场景一致性约束

1. `objectRefs` 与 `stage.objectRefs` 必须引用 M1 已存在的聚合根；同一场景内出现的对象不得是同一聚合的内部子实体。
2. `actorRefs` 与 `stage.roleRef` 必须引用 M5 已存在的角色；每个阶段的 `roleRef` 必须包含在场景 `actorRefs` 中。
3. `triggerBehaviorRef` 必须存在于 M2，并与 M6 对应流程的 `trigger.behaviorRef` 一致；不一致时以 M6 为准并修正场景。
4. `flowRefs` 与 `stage.flowRef` 必须引用 M6 已存在的流程；`stage.stageType=FLOW_CALL` 时该阶段必须声明 `flowRef`；整个流程引用图不得出现循环。
5. 每个阶段只能声明一个主执行引用：`BEHAVIOR_CALL` 必须有 `behaviorRef`，`FLOW_CALL` 必须有 `flowRef`，`RULE_EVALUATE` 必须有 `ruleRef`，`WAIT` 与 `SYSTEM_TASK` 不得声明以上三者中的业务引用。
6. 场景不得定义活动节点、网关、分支、审批结果、超时约束、权限或界面元素；出现这类内容视为越界，应移入 M6、M5 或 MU。
7. `stages` 中至少有一个阶段的 `isTerminal=true`；从首个阶段到每个终止阶段必须存在可达路径。
8. `endRules` 应覆盖正常结束、异常结束与提前结束三类情形；某类情形不适用时可省略并说明原因，不得三类全部缺失。
9. 场景中声明的结束触发行为必须与 M2 该行为的 `syncTriggers` 一致，禁止在场景中重新定义跨对象联动链。
10. 场景的 `objectRefs` 与 MU 对应屏幕的 `objectAccess` 必须一致：场景中 `stageType=BEHAVIOR_CALL` 的阶段涉及的对象，必须在对应屏幕的依赖对象清单中出现（只读或可写均可）。

# 第六章  M5 主体模型

## 6.1  设计目标

主体模型解决"**谁能做什么、谁看得见什么**"的问题，采用 RBAC（基于角色的访问控制）为基础，支持 ABAC（基于属性的访问控制）扩展。

> **设计决策**：权限定义不内嵌于行为模型，也不内嵌于界面模型。行为模型只声明 `requiredPermissions`，界面模型的操作功能点只声明 `permissionRef`，权限的授予关系与授予对象全部在主体模型中定义。这样角色权限的变化不影响行为模型与界面模型定义。

> **权限分层**：本版本把权限目标由"行为 / 实体"两级扩展为**菜单、屏幕、操作功能点、行为、实体**五类，使"能不能看到菜单""能不能进入界面""进去之后能不能点这个按钮""后端是否放行"四个问题都有唯一权威答案。

## 6.2  模型层次

| 层次                   | 说明                                                                   |
| -------------------- | -------------------------------------------------------------------- |
| 参与者（Actor）           | 与系统交互的主体，分为：人类用户（HUMAN）、系统账户（SYSTEM）                                 |
| 角色（Role）             | 权限的集合单元，一个参与者可拥有多个角色，角色支持继承；分为人工岗位角色与系统自动执行角色                        |
| 权限（Permission）       | 对菜单、屏幕、操作功能点、行为或实体数据的授权，是本文档最小的权限单元                                  |
| 权限组（PermissionGroup） | 权限的分组管理，便于批量授予                                                       |
| 权限目标类型（Target Type）  | `MENU` / `SCREEN` / `ACTION_POINT` / `BEHAVIOR` / `ENTITY`，决定该权限控制什么 |

## 6.3  模型元素规范

### 6.3.1  参与者（Actor）

| 属性名         | 类型        | 说明                                                         |
| ----------- | --------- | ---------------------------------------------------------- |
| actorId     | String    | 主体唯一标识                                                     |
| name        | String    | 主体名称（岗位名或系统账号名）                                            |
| actorType   | Enum      | `HUMAN` / `SYSTEM`                                         |
| identityRef | String    | 可选；关联 M1 人员对象的编号（人员编号），用于把登录账号映射到人员；`actorType=SYSTEM` 时不填 |
| roles       | RoleRef[] | 拥有的角色列表                                                    |
| attributes  | Map       | 主体属性（用于 ABAC 条件评估，如 `departmentId`、`level`、`ownerId`）      |
| enabled     | Boolean   | 主体是否启用；停用后不再参与权限解析                                         |


### 6.3.2  角色（Role）

角色除了承载权限集合，也是 M6 人工任务的唯一参与人类型、M4 场景阶段的唯一责任主体类型。删除或重命名角色前，必须分析所有 M2 `requiredPermissions`、M5 权限项、M6 流程中的 `roleRefs` 与活动 `roleRef`、M4 场景的 `actorRefs` 与 `stage.roleRef`、MU 中 `menu.permissionRef` 与 `actionPoint.permissionRef`。

| 属性名              | 类型              | 说明                                                                |
| ---------------- | --------------- | ----------------------------------------------------------------- |
| roleId           | String          | 角色唯一标识，建议格式 `ROLE-{NN}` 或 `ROLE-{DOMAIN}-{NAME}`                  |
| name             | String          | 角色名称                                                              |
| roleType         | Enum            | `HUMAN_ROLE`（人工岗位）/ `SYSTEM_ROLE`（系统自动执行主体）                       |
| description      | String          | 角色职责边界一句话说明                                                       |
| inheritsFrom     | RoleRef[]       | 继承的父角色（支持多继承）                                                     |
| permissions      | PermissionRef[] | 直接授予的权限列表                                                         |
| permissionGroups | GroupRef[]      | 授予的权限组                                                            |
| dataScope        | Enum            | 角色级默认数据范围：`ALL` / `OWN` / `DEPT` / `CUSTOM`；可被权限项级 `dataScope` 覆盖 |
| enabled          | Boolean         | 角色是否启用                                                            |

**角色约束（强制）**：

1. `SYSTEM_ROLE` 只持有 `BEHAVIOR` 权限，不得持有 `MENU` / `SCREEN` / `ACTION_POINT` 权限，也不参与菜单渲染；
2. 一个主体拥有多个角色时，权限取**并集**；同一权限目标同时出现 `ALLOW` 与 `DENY` 时，`DENY` 优先；
3. 角色继承时，子角色有效权限 = 自身权限 ∪ 全部父角色权限（递归展开，按第 2 条消解冲突）；
4. 角色继承链不得出现环；
5. `dataScope=DEPT` 时必须同时给出判定字段（如 `departmentId`），并明确"本部门"为**精确相等、不含下级**。

### 6.3.3  权限（Permission）

| 属性名           | 类型      | 说明                                                                                    |
| ------------- | ------- | ------------------------------------------------------------------------------------- |
| permissionId  | String  | 权限标识，命名约定见 §6.3.4                                                                     |
| name          | String  | 权限名称（业务可读，如"合同管理菜单可见""提交按钮可用"）                                                        |
| targetType    | Enum    | `MENU` / `SCREEN` / `ACTION_POINT` / `BEHAVIOR` / `ENTITY`                            |
| targetRef     | Ref     | 授权目标引用，对应关系见 §6.3.4                                                                   |
| effect        | Enum    | `ALLOW` / `DENY`；同一角色对同一目标出现 `DENY` 时以 `DENY` 为准                                      |
| dataScope     | Enum    | 数据范围：`ALL` / `OWN` / `DEPT` / `CUSTOM`；`MENU` / `SCREEN` / `ACTION_POINT` 类型通常为 `ALL` |
| abacCondition | String  | ABAC 条件表达式，如 `actor.departmentId == resource.departmentId`                            |
| enabled       | Boolean | 权限是否启用                                                                                |


### 6.3.4  四级权限目标与分配规则（强制）

| targetType     | targetRef 指向                  | 决定什么                                     | 在何处声明                                     | 未授权时的界面表现   |
| -------------- | ----------------------------- | ---------------------------------------- | ----------------------------------------- | ----------- |
| `MENU`         | MU `menus.menuId`             | 该角色登录后左侧菜单是否渲染该项                         | M5 角色权限配置                                 | 菜单不渲染       |
| `SCREEN`       | MU `screens.screenId`         | 能否进入该界面（同一屏幕被多个菜单复用时的补充控制）               | M5 角色权限配置                                 | 菜单可见但进入被拒   |
| `ACTION_POINT` | MU `screens.actions.actionId` | 界面内某个操作功能点（按钮）是否可用、是否渲染                  | M5 角色权限配置                                 | 按钮置灰或按规则不渲染 |
| `BEHAVIOR`     | M2 `behaviors.id`             | 能否执行该行为（**后端强制校验**）                      | M5 角色权限配置 + M2 `requiredPermissions` 反向绑定 | 后端拒绝并返回业务提示 |
| `ENTITY`       | M1 `aggregates.id`            | 数据可见范围（配合 `dataScope` 与 `abacCondition`） | M5 角色权限配置                                 | 查询结果按数据范围过滤 |

**权限标识命名约定**：

| 目标类型           | 命名格式                                | 示例                                                        |
| -------------- | ----------------------------------- | --------------------------------------------------------- |
| `MENU`         | `PERM-MENU-{menuId 去掉 menu- 前缀，大写}` | `menu-contract-maintain` → `PERM-MENU-CONTRACT-MAINTAIN`  |
| `SCREEN`       | `PERM-SCREEN-{screenId 大写}`         | `frmContractApproval` → `PERM-SCREEN-FRMCONTRACTAPPROVAL` |
| `ACTION_POINT` | `PERM-ACT-{actionId 大驼峰转连字符，大写}`    | `actSaveDraft` → `PERM-ACT-SAVE-DRAFT`                    |
| `BEHAVIOR`     | `PERM-BEH-{behaviorId 大写}`          | `Contract_SaveAsDraft` → `PERM-BEH-CONTRACT-SAVEASDRAFT`  |
| `ENTITY`       | `PERM-ENT-{aggregateId 大写}`         | `AGG-CONTRACT-001` → `PERM-ENT-AGG-CONTRACT-001`          |

**分配强制规则**：

1. **每一个菜单都必须有对应的 `MENU` 权限**，且该权限至少被一个角色授予；没有角色可见的菜单不得存在于菜单树；
2. **每一个操作功能点（按钮）都必须有对应的 `ACTION_POINT` 权限**，且该权限至少被一个角色授予；无角色可用的按钮不得出现在界面上；
3. **每一个 `triggerType=USER_ACTION` 的 M2 行为都必须有对应的 `BEHAVIOR` 权限**，并在 M2 的 `requiredPermissions` 中声明；
4. **一级菜单可见性规则**：只要该一级菜单下存在至少一个对该角色可见的二级菜单，一级菜单即渲染；否则整个一级菜单隐藏；
5. **双层校验**：界面按 `ACTION_POINT` 权限渲染按钮的可用性（前端），后端在执行前仍必须按 `BEHAVIOR` 权限再次校验，两者不得互相替代；
6. **系统自动执行主体例外**：`SYSTEM_ROLE` 只持有 `BEHAVIOR` 权限，菜单、屏幕与操作功能点权限对其无意义；
7. `ACTION_POINT` 权限的授权结果必须与"该功能点所属行为的 `BEHAVIOR` 权限"一致：能点按钮的角色必须同时拥有对应行为权限，反之亦然（权限一致性核对项）。

### 6.3.5  权限组（PermissionGroup）

| 属性名            | 类型              | 说明                        |
| -------------- | --------------- | ------------------------- |
| groupId        | String          | 权限组标识                     |
| name           | String          | 权限组名称，如"合同维护-全部按钮"        |
| targetType     | Enum            | 组内权限的统一目标类型；一组只放同一目标类型的权限 |
| permissionRefs | PermissionRef[] | 组内权限列表                    |
| description    | String          | 用途说明                      |

### 6.3.6  权限分配矩阵（强制）

主体模型必须给出一张**权限分配矩阵**作为角色配置的唯一权威输入，形如：

| 权限目标（菜单 / 功能点）     | 角色甲 | 角色乙 | 角色丙 |
| ------------------ | --- | --- | --- |
| 菜单：合同管理 / 合同维护     | 可见  | 可见  | —   |
| 菜单：合同管理 / 合同查询     | 可见  | 可见  | 可见  |
| 功能点：FUNC-01 保存合同草稿 | 允许  | 允许  | 否   |
| 功能点：FUNC-02 提交合同审批 | 允许  | 允许  | 否   |

矩阵要求：

1. 行必须覆盖全部 `MENU` 权限与全部 `ACTION_POINT` 权限，不得遗漏；
2. 单元格取值只允许 `可见` / `允许` / `—`（不适用） / `否`（适用但禁止）；
3. 矩阵是角色配置的输入；角色的创建、人员与角色的绑定由外部账号体系承载，主体模型只定义角色与权限的对应关系；
4. 矩阵与 MU 的 `menu.permissionRef`、`actionPoint.permissionRef` 必须双向一致。

# 第七章  M6 流程模型

## 7.1  设计目标与边界

M6 流程模型定义业务工作如何从开始流转到结束，承载两类流程：

1. `COLLABORATION`：端到端业务协同流，例如合同创建、审批、生效、开票、收款和关闭；
2. `APPROVAL`：围绕提交、审批、会签、驳回、退回和通过形成的审批流，可被协同流作为子流程调用。

M6 负责角色任务、系统活动、顺序、并行、条件网关和子流程调用。M6 不重新定义对象、行为、规则或角色，而是通过稳定 ID 引用其他模型。

> **强制角色约束**：所有 `USER_TASK` 和 `APPROVAL_TASK` 的参与人只能通过 `roleRef` 引用 M5 `roles.roleId`。不得引用 `actorId`，不得填写"财务经理"等自由文本，也不得直接绑定具体用户。

> **与 M4 场景模型的分工**：端到端业务场景的业务语义（业务目标、起止条件、业务阶段与责任角色、涉及对象、结束触发规则）在 M4 场景模型中定义；M6 只定义流程实例如何推进——活动节点、网关、分支、子流程调用与审批结果。引用方向为 M4 → M6，M6 不反向引用 M4。跨对象联动已由 M2 `syncTriggers` 承载，流程只编排粗粒度业务阶段与审批节点。

## 7.2  流程类型及组合关系

### 7.2.1  端到端业务协同流（COLLABORATION）

端到端协同流描述一个业务目标跨阶段、跨对象的完整生命周期，是本框架中的**可执行编排**：业务目标、起止条件、阶段划分与责任角色由对应的 M4 场景声明，本处只定义这些阶段如何展开为活动节点与网关。协同流可以调用 M2 行为、M6 审批子流程。

```text
合同创建（保存草稿/提交）
-> 调用合同审批子流程
-> 合同生效
-> 合同开票
-> 合同收款
-> 合同关闭
```

### 7.2.2  审批流（APPROVAL）

审批流描述由角色承担的人工决策过程。审批条件可直接使用流程表达式，也可通过 `ruleRef` 引用 M3 规则。金额、数量、状态、组织层级等可复用业务判断应优先进入 M3。

```text
合同提交
-> 财务经理审批
-> 合同金额判断
   -> 不超过 100 万元：审批通过
   -> 超过 100 万元：总经理审批
-> 审批完成
```

## 7.5  流程约束

1. 每条流程必须有且仅有一个 `startActivity`，并至少有一个 `endActivities`；
2. 除 `END` 外的可达活动必须存在合法后继路径；所有 `endActivities` 必须指向 `END` 活动；
3. `USER_TASK`、`APPROVAL_TASK` 必须填写有效 `roleRef`，且该角色必须包含在流程 `roleRefs` 中；
4. `GATEWAY` 至少有两个分支，最多一个默认分支；非默认分支必须提供 `ruleRef` 或 `conditionExpression` 或 `approvalOutcome`；
5. `SUB_FLOW_CALL` 不得形成直接或间接递归调用环；
6. 审批活动的处理结果必须显式覆盖通过、驳回、退回等实际业务结果，不得只有成功路径；
7. 流程局部条件可使用表达式；跨流程复用、跨对象或复杂决策应定义为 M3 规则并通过 `ruleRef` 引用；
8. 跨对象联动已由 M2 `syncTriggers` 承载，流程中可用 `SYSTEM_TASK` 标注联动触发的结果活动，但不得重复定义联动逻辑。

## 7.6  跨模型引用矩阵

| M6 字段                                        | 引用目标               | 一致性要求                     |
| -------------------------------------------- | ------------------ | ------------------------- |
| `businessObjectRefs`                         | M1 `aggregates.id` | 引用对象必须存在                  |
| `roleRefs`、`activity.roleRef`                | M5 `roles.roleId`  | 只允许角色，活动角色必须属于流程 roleRefs |
| `trigger.behaviorRef`、`activity.behaviorRef` | M2 `behaviors.id`  | 引用行为必须存在                  |
| `activity.ruleRef`、`branch.ruleRef`          | M3 `rules.id`      | 规则必须无副作用，流程只消费判断结果        |
| `activity.subFlowRef`                        | M6 `flows.id`      | 子流程必须存在，且整个调用图无环          |

> 说明：M4 场景模型通过 `flowRefs` 与 `stage.flowRef` 引用 M6 流程，引用方向为 M4 → M6。校验时 M6 只作为被引用方，检查流程存在性与调用图无环性；M6 不校验也不引用 M4。

# 第八章  M7 查询统计与报表模型

## 8.1  设计目标与边界

M7 定义业务应用中的查询统计对象和固定报表对象，专门承载多个 M1 业务对象之间的关联查询、条件过滤、结果列、分组聚合、排序、分页和可选参考 SQL。

M7 不是 BI 指标模型，不定义事实表、维度表、宽表、数据集市、OLAP Cube、ETL 任务或自助分析语义。M7 也不定义独立指标资产；`COUNT`、`SUM`、`AVG`、`MIN`、`MAX` 等只作为具体查询对象内部的聚合表达式存在。

M7 的直接依赖严格限制为：

```text
M7 查询统计或报表对象 -> M1 对象及字段
M7 查询统计或报表对象 <-> M2 QUERY 行为（一对一）
```

M7 不直接引用 M3 规则、M5 主体或 M6 流程。查询条件、关联条件、聚合公式属于查询对象自身定义，不视为 M3 业务规则。数据访问权限暂不在 M7 建模，仍由 M2 行为通过 `requiredPermissions` 与 M5 建立关系。

> **说明**：参考 SQL 为可选。物理表名在实现阶段确定，M7 的语义定义（来源 / 条件 / 结果列 / 聚合）才是稳定业务语义，参考 SQL 仅作实现指导。

## 8.2  M2 查询行为与 M7 对象的分界

| 判断问题    | M2 QUERY 行为                  | M7 查询统计与报表对象           |
| ------- | ---------------------------- | ---------------------- |
| 核心职责    | 定义"执行一次查询或生成报表"的原子行为         | 定义"查什么、如何关联、如何统计、返回什么" |
| 单聚合简单查询 | 可独立定义，不要求 M7                 | 通常不建立                  |
| 跨对象关联查询 | 通过 queryReportRef 调用 M7      | 定义来源对象、Join、条件和结果列     |
| 分组统计    | 负责执行入口                       | 定义聚合、GROUP BY、HAVING   |
| 固定报表    | 负责生成或导出行为                    | 定义报表列、分组、小计、合计和导出格式    |
| 权限      | 通过 requiredPermissions 关联 M5 | 不定义权限或角色               |

一条 M2 行为最多引用一个 M7 对象，一个 M7 对象也必须且只能绑定一条 M2 行为。

## 8.3  对象类型

| objectType          | 说明                       | 典型示例       |
| ------------------- | ------------------------ | ---------- |
| `DETAIL_QUERY`      | 跨对象详情查询，返回一条主要业务记录及关联信息  | 合同执行详情     |
| `LIST_QUERY`        | 跨对象条件列表查询，通常支持分页和排序      | 已开票未收款合同列表 |
| `STATISTICAL_QUERY` | 包含聚合或分组统计的查询分析           | 按部门统计合同金额  |
| `REPORT`            | 具有固定列、分组、小计、合计和导出要求的业务报表 | 部门合同执行汇总报表 |

```yaml
        label: 已收款金额
        dataType: Decimal
        sourceExpression: receiptAgg.receivedAmount
        aggregateFunction: MAX
        format: "#,##0.00"
      - name: unreceivedAmount
        label: 未收款金额
        dataType: Decimal
        sourceExpression: "MAX(contract.totalAmount) - COALESCE(MAX(receiptAgg.receivedAmount), 0)"
        aggregateFunction: NONE
        format: "#,##0.00"
      - name: receiptRate
        label: 收款完成率
        dataType: Decimal
        sourceExpression: "COALESCE(MAX(receiptAgg.receivedAmount), 0) / NULLIF(MAX(contract.totalAmount), 0)"
        aggregateFunction: NONE
        format: "0.00%"
    groupBy:
      - contract.contractNo
      - contract.contractName
    having: []
    orderBy:
      - expression: contract.signDate
        direction: DESC
    pagination:
      enabled: true
      defaultPageSize: 20
      maxPageSize: 200
    reportOptions: null
    referenceSql: null
    version: "1.0"
```

## 8.6  依赖与一致性约束

1. M7 `sourceObjects.objectRef` 必须引用 M1 已存在的聚合根；字段路径必须可解析到 M1；
2. 每个 M7 对象必须填写唯一 `behaviorRef`，目标必须是 M2 `behaviorType=QUERY` 的行为；
3. M2 `queryReportRef` 与 M7 `behaviorRef` 必须双向一致、严格一对一；
4. M7 不得出现 `ruleRefs`、`requiredPermissions`、`roleRefs`、`flowRefs` 等跨模型字段；
5. 每个查询来源别名必须唯一，且必须有且仅有一个 `primary=true` 的主对象；
6. 两个或更多一对多来源同时参与聚合时，必须通过 `preAggregation` 分别按 Join 键汇总后再关联，禁止以 `SUM(DISTINCT amount)` 代替正确的预聚合；
7. `objectType=REPORT` 必须填写 `reportOptions`；其他类型的 `reportOptions` 应为空；
8. `referenceSql` 可选；若填写，其参数绑定与结果映射必须与语义定义一致。

# 第九章  MU UI 模型

## 9.1  设计目标与边界

**设计目标**：MU 是八个模型的**入口层/追溯层**，定义"用户在哪里操作、看到哪些元素、点哪个功能点、驱动哪个行为、由哪个权限控制"，把界面与业务模型用稳定 ID 连成完整调用链。本版 MU 采用**层级导航结构**，自上而下为：

```text
总体界面（应用入口）
  -> 一级菜单（分组，不关联屏幕）
      -> 二级菜单（强制存在，关联屏幕，绑定 MENU 权限）
          -> UI 界面（屏幕：区块 Panel + ASCII 布局 + 界面元素 Element）
              -> 操作功能点（ActionPoint，对应 M2 行为 + M5 ACTION_POINT 权限）
```

**边界（强制）**：

1. **只引用、不重定义**：MU 只通过稳定 ID 引用 M1/M2/M5/M6/M7，不重新定义对象、行为、规则、角色、权限、流程或报表；
2. **不承载视觉设计**：配色、字体、像素级布局、图标资源、皮肤属于设计系统/原型/主题，不在本模型；ASCII 布局只表达区域划分与控件排布；
3. **不定义权限**：菜单可见性、按钮可用性由 M5 主体模型的 `MENU` 与 `ACTION_POINT` 权限决定；MU 只通过 `permissionRef` 引用，不得自行定义角色或权限；
4. **不替代 M6**：端到端与审批流转归 M6；MU 只声明操作功能点与行为入口的对应关系，以及"哪个按钮启动哪条流程"的引用；
5. **不承载业务校验公式**：输入校验引用 M3 规则或 M1 属性约束；控件级格式（掩码、联动启用）可作为元素属性，仅限本元素内；
6. **界面事件联动只做前端**：`linkageRules` 只描述前端计算、提示与显隐，不得声明任何对象状态变更；跨对象联动归 M2 `syncTriggers`；
7. 纯展示界面允许无操作功能点，但必须存在界面元素。

## 9.2  模型元素规范

### 9.2.1  应用（Application）

| menus | Menu[] | 一级菜单集合   |

### 9.2.2  菜单（Menu）

| 属性名           | 类型            | 说明                                |
| ------------- | ------------- | --------------------------------- |
| menuId        | String        | 菜单唯一标识                            |
| name          | String        | 菜单名称                              |
| permissionRef | PermissionRef | **必填**；控制本菜单可见性的 M5 `MENU` 权限     |
| children      | Menu[]        | 二级菜单集合（**强制至少一个**）                |
| screenRef     | ScreenRef     | 二级菜单关联的屏幕 `screenId`（一级菜单不直接关联屏幕） |

约束：

1. 菜单层级固定为**两级**：一级菜单 → 二级菜单；
2. 一级菜单必须包含至少一个二级菜单，即使业务上仅有一个子项；

### 9.2.4  界面区块（Panel）

区块是屏内部的版面分区，用于把元素按视觉位置与业务用途分组。需求说明书「界面元素表」中的分组标题行（如「主表字段」「从表：明细对象名」「查询条件区」「操作按钮（功能点）」「新增 / 编辑弹窗」）就是区块。

| 属性名         | 类型      | 说明                                                                             |
| ----------- | ------- | ------------------------------------------------------------------------------ |
| panelId     | String  | 区块标识，屏幕内唯一                                                                     |
| name        | String  | 区块名称，如"顶部工具区""主表区""从表：合同付款阶段""汇总区""操作按钮区""查询条件区""待办列表区""审批处理区""列表区""新增 / 编辑弹窗" |
| order       | Integer | 区块在屏幕中的自上而下顺序，从 1 开始，不得重复                                                      |
| description | String  | 区块用途说明（可选）                                                                     |

**区块划分要求（强制）**：

1. 每个元素必须归属且只归属一个区块（`Element.panelRef`）；
2. 区块清单必须覆盖屏幕上出现的全部元素，不得有元素落在所有区块之外；
3. 主从表界面必须至少区分「主表区」与「从表：{明细对象名}」，不得混列；
4. 界面元素若属于循环出现的明细行，区块名称为「从表：{明细对象名}」，元素 `id` 采用 `{明细表格控件名}.{列名}` 形式；
5. 弹窗内的元素与其触发按钮**分属不同区块**（触发按钮在工具栏 / 列表行区块，表单字段在「新增 / 编辑弹窗」区块）。

### 9.2.5  界面元素（Element）

界面元素是屏幕内可呈现、可操作的最小单位，也是"界面 ↔ 对象属性"的唯一映射点。**每个元素必须逐项声明 §9.7 规定的十项关键属性。**

| 属性名           | 类型              | 说明                                                                                                                                                      |
| ------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| id            | String          | 控件 ID（元素标识），屏幕内唯一。命名约定：文本框 `txt*`、多行文本 `txta*`、下拉 `cbo*`、日期 `dtp*`、跳选框 `psl*`、数字框 `num*`、表格 `grd*`、标签 `lbl*`、按钮 `btn*`、弹窗控件 `dlg*`、查询条件 `q*`、分页 `pager` |
| name          | String          | 字段项名称（界面显示标签），对应需求说明书「界面元素表」的「字段项」列                                                                                                                     |
| panelRef      | PanelRef        | 所属界面区块，引用本屏幕 `panels[].panelId`                                                                                                                         |
| type          | Enum            | 控件类型，见 §9.2.10                                                                                                                                          |
| io            | Enum            | `I`（输入）/ `O`（输出 / 只读）/ `I_O`（输入输出）；空表示纯展示标签。**需求说明书「可编辑」列 = `io` 的界面化表达：`I`→是、`O`→否、`I_O`→是**                                                           |
| required      | Boolean         | 是否必填；必须与 M1 属性 `required` 及 M3 规则一致；不适用填 `—`                                                                                                            |
| dataBinding   | FieldPath       | 绑定的 M1 属性路径，如 `Contract.contractName`；从表列用 `PaymentStage.stageNo`；按钮类元素不填                                                                               |
| sourceType    | Enum            | 数据来源类型，见 §9.4                                                                                                                                           |
| dataSource    | Ref             | 数据源：字典 ID（`DICT-xxx`）、引用对象（M1 聚合根 ID）、报表对象（M7 对象 ID）、编号规则（`缩写-YYYYMMDD-NNNN`）、计算表达式，或系统来源（当前登录人 / 服务器时间 / 选中行）                                          |
| defaultValue  | String          | 默认值：`空` / `自动生成` / `字典首项` / `当前登录人` / `当前登录人所属部门` / `保存时` / `实时计算` 等                                                                                    |
| boundBehavior | String          | 对应行为 / 说明：功能点编号（`FUNC-xx` / `Q-xx` / `B-xx` / `B-APP-xx`）、规则编号（`REF-xx` / `INV-xx` / `R-xx`）或元素级说明                                                      |

### 9.2.6  操作功能点（ActionPoint）

操作功能点是界面与行为模型的衔接点，对应"界面上的一个按钮/动作 → 调用一个 M2 行为"，并必须绑定一个 M5 `ACTION_POINT` 权限。

| 属性名           | 类型            | 说明                                                                                                                      |
| ------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| actionId      | String        | 功能点唯一标识                                                                                                                 |
| name          | String        | 功能点名称（按钮文案）                                                                                                             |
| elementRef    | ElementRef    | 对应的界面元素 `id`（按钮类元素）                                                                                                     |
| behaviorRef   | BehaviorRef   | 对应调用的 M2 行为                                                                                                             |
| actionType    | Enum          | `BUTTON`（普通按钮）/ `SUBMIT`（提交）/ `DRAFT`（保存草稿）/ `APPROVE`（审批通过）/ `REJECT`（审批驳回）/ `RETURN`（审批退回）/ `QUERY`（查询）/ `EXPORT`（导出） |
| permissionRef | PermissionRef | **必填**；控制本功能点可用性的 M5 `ACTION_POINT` 权限                                                                                  |
| availableWhen | String        | 可用条件（业务可读），如"仅草稿态可用""仅首节点未处理时可用""本人提交的单据"                                                                               |
| flowRef       | FlowRef       | 可选；本功能点启动的 M6 流程（提交类按钮）                                                                                                 |
| description   | String        | 补充说明                                                                                                                    |

约束：

1. 一个界面元素可以对应**多个操作功能点**，按登录角色或单据状态解析（如审批界面的「通过 / 驳回」按钮：财务经理解析为合同审批行为的财务节点，总经理解析为总经理节点）；此时各功能点分别声明 `availableWhen` 与 `permissionRef`；
2. `frontendOnly=true` 的元素不得设操作功能点；
3. 每个操作功能点必须声明 `permissionRef`，且该权限的 `targetType=ACTION_POINT`、`targetRef` 等于本 `actionId`。

| scopeNote       | String       | 范围说明，如"仅草稿态允许物理删除，提交后只允许作废 / 归档""仅状态字段可改""随草稿合同级联删除"              |

### 9.2.8  界面初始化规则（InitRule）

| 属性名      | 类型     | 说明                                                                                                                                                       |
| -------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| initItem | Enum   | 初始化项：`DEFAULT_VALUE`（默认值）/ `INITIAL_DATA`（初始载入数据）/ `CONTEXT_PASSING`（上下文带值）/ `EDITABILITY`（只读 / 可编辑态判定）/ `BUTTON_STATE`（按钮可用性）/ `UNSAVED_LEAVE`（未保存离开提示） |

2. 屏幕存在下拉 / 弹窗候选数据时，必须声明 `INITIAL_DATA`（含"仅启用项"等过滤口径）；
3. 屏幕存在状态相关的只读 / 可编辑切换时，必须声明 `EDITABILITY` 与 `BUTTON_STATE`，两者都必须逐状态枚举；
4. 界面为"列表新增"或"详情入口"时，必须声明 `CONTEXT_PASSING`。

### 9.2.9  界面事件联动规则（LinkageRule）

| 属性名      | 类型      | 说明                                                               |
| -------- | ------- | ---------------------------------------------------------------- |
| seq      | Integer | 序号                                                               |
| trigger  | String  | 触发字段 / 动作，如"输入 / 修改「付款比例」"                                       |
| effect   | String  | 联动效果，如"实时计算该行「阶段应付金额」并刷新底部合计"                                    |
| kind     | Enum    | `FRONTEND_ONLY`（纯前端计算 / 显隐）/ `VALIDATE_HINT`（仅提示，不拦截）            |
| boundary | String  | 边界说明；`VALIDATE_HINT` 必须写明真实拦截由哪条 `REF-xx` / `INV-xx` / `R-xx` 承担 |

**强制边界**：`linkageRules` 不得声明任何对象状态变更、不得声明跨对象写操作、不得写入 M2 `syncTriggers`。跨对象联动一律由 M2 行为的 `syncTriggers`（配 M3 规则判断）在执行行为时自然处理。

## 9.5  ASCII 界面布局规则（强制）

**布局总则（强制）**：表单属性标签一律**右对齐**（文字末尾对齐）、控件一律**左对齐**，标签列采用固定宽度，形成规整的「标签列 + 控件列」表格化布局。

ASCII 布局图是屏幕结构化布局的轻量表达，描述"控件位于哪个区域、如何排布"，**不描述视觉样式**。绘制约定：

- 等宽字符绘制，每行不超过 100 字符；
- 边框使用 `┌ ─ ┐ └ ┘ │ ├ ┤` 绘制区域边界；
- 控件标注：`[elementId]` 文本框/按钮、`(cboId)` 下拉框、`{dtpId}` 日期、`[pslId…]` 跳选框、`@grdId` 表格；
- 布局中出现的每个 elementId 必须存在于该屏幕 `elements`，且 `io`/`required` 与 `elements` 对齐；
- 区块顺序必须与 `panels[].order` 一致。

## 9.6  审批功能的双按钮规则（强制）

如果一个功能（屏幕）本身带审批流，那么该屏幕在"创建/录入"时**必须提供两个独立的按钮功能点**：

1. **保存草稿**（`actionType=DRAFT`）：仅保存数据，将对象置于"草稿"状态，不触发审批；对应 M2 的 `Contract_SaveAsDraft` 行为；
2. **提交**（`actionType=SUBMIT`）：保存数据并提交进入审批流，对应 M2 的 `Contract_Submit` 行为（该行为将对象置于"待审批"状态，并作为审批流的启动入口）。

约束：

- 两个按钮必须是**独立的功能点**，分别对应独立的 M2 行为，不得合并为一个"保存"按钮；
- 两个按钮分别绑定独立的 M5 `ACTION_POINT` 权限，可分别授予不同角色；
- 提交行为在 M6 审批流中以 `trigger.behaviorRef` 引用，作为审批流启动入口，并在 MU 的 `actions[].flowRef` 与屏幕 `flowEntryRefs` 中登记；
- 无审批流的功能不需要"保存草稿/提交"双按钮，只需"保存"按钮。

## 9.7  界面元素的关键属性清单（强制）

**每个界面元素必须逐项声明下列十项关键属性，缺一不可**（按钮类元素除 `id`/`name`/`panelRef`/`type`/`boundBehavior` 外，其余填 `—`）。这十项与需求说明书第九部分「界面元素表」的列一一对应，保证"界面元素"在需求侧与本体侧是同一份清单的两种表达。

| #  | 需求说明书「界面元素表」列 | MU 属性                   | 必填         | 说明                                        |
| -- | ------------- | ----------------------- | ---------- | ----------------------------------------- |
| 1  | 字段项           | `Element.name`          | 是          | 界面显示标签                                    |

## 9.9  一致性约束（MU 门禁）

1. `element.dataBinding` 字段路径必须可解析到 M1 聚合属性；按钮类元素除外；
2. `element.dataSource` 引用的 M7 对象、`element.dataSource` 中的字典 ID 必须存在；
3. `element.panelRef` 必须指向本屏幕 `panels[].panelId`；`panels[].order` 必须唯一且连续覆盖全部元素；
4. 每个元素必须逐项声明 §9.7 规定的十项关键属性；按钮类元素除 `id`/`name`/`panelRef`/`type`/`boundBehavior` 外其余填 `—`；
5. 每个操作功能点必须声明 `permissionRef`，且对应 M5 权限的 `targetType=ACTION_POINT`、`targetRef` 等于该 `actionId`；`frontendOnly=true` 的元素不得设操作功能点；
6. 带审批流的功能屏幕必须同时包含 `DRAFT` 与 `SUBMIT` 两个功能点；
7. **反向门禁**：M2 中 `triggerType=USER_ACTION` 的行为必须被至少一个 MU 操作功能点引用；
8. 控件类型必须遵循 §9.3 映射规则（日期→DATEPICKER、枚举/字典→COMBO、对象引用→POPUP_SELECT、派生计算→LABEL + `sourceType=DERIVED`）；
9. 屏幕布局必须遵循 §9.5 布局规则（单表 2 列、主从主表 3 列 + 从表表格、查询条件 3 列 + 结果表格分页、**列表维护界面为「工具栏 + 列表」且新增/编辑走弹窗**、审批处理界面单据信息全只读、报表查询界面含合计行）；
10. `layout` 中出现的 elementId 必须存在于该屏幕 `elements`，且 `io`/`required` 标注一致；
11. 二级菜单必须关联屏幕并声明 `permissionRef`，且每级一级菜单下至少存在一个二级菜单；一级菜单可见性由子菜单聚合；
12. 屏幕存在系统生成字段 / 候选数据 / 状态相关只读切换时，`initRules` 必须覆盖 `DEFAULT_VALUE` / `INITIAL_DATA` / `EDITABILITY` / `BUTTON_STATE`；
13. `linkageRules` 不得声明对象状态变更或跨对象写操作；`kind=VALIDATE_HINT` 时必须写明真实拦截的规则编号；
14. `objectAccess` 必须与 M4 场景中涉及本屏幕的阶段对象一致；`deleteSemantics` 必须与 `scopeNote` 的表述一致；
15. 屏幕 `actions[].flowRef` 与 `flowEntryRefs` 必须引用 M6 已存在的流程。

| 领域概念、数据及聚合边界                   | 完整覆盖         | M1 对象模型                                               |
| 原子功能、命令与查询入口                   | 完整覆盖         | M2 行为模型                                               |
| 业务规则与一致性约束                     | 完整覆盖         | M1 内置约束、refRules、invariants + M3 规则模型                 |
| 跨对象同步联动                        | 完整覆盖         | M2 `syncTriggers` + M3 规则（被同步调用）                      |
| 端到端业务流程的业务语义                   | 完整覆盖         | M4 场景模型（业务目标、起止条件、业务阶段与责任角色、涉及对象、结束触发规则）              |
| 端到端业务流程的可执行编排                  | 完整覆盖         | M6 `COLLABORATION` 流程（活动节点、网关、分支、子流程调用）               |
| 人工审批流                          | 完整覆盖         | M6 `APPROVAL` 流程 + M5 角色                              |
| 角色、权限                          | 完整覆盖         | M5 主体模型：菜单可见性 / 屏幕进入 / 操作功能点可用性 / 行为授权 / 实体数据范围五类权限目标 |
| 菜单导航与界面结构                      | 完整覆盖         | MU UI 模型（菜单树 + 屏幕区块 + ASCII 布局）                       |
| 界面元素与字段级定义                     | 完整覆盖         | MU UI 模型（每个元素十项关键属性）+ M1 属性约束                         |
| 界面初始化与界面事件联动                   | 完整覆盖         | MU `initRules` / `linkageRules`（纯前端，不改变对象状态）          |
| 跨对象查询、统计分析                     | 完整覆盖         | M7 查询统计对象 + 一对一 M2 QUERY 行为                           |
| 固定业务报表                         | 完整覆盖         | M7 REPORT 对象 + 一对一 M2 QUERY 行为                        |
| 异常、驳回、退回路径                     | 主要语义覆盖       | M2 前后置条件、M4 结束触发规则、M6 分支与终止路径                         |
| 对象到数据库表的映射                     | 框架外          | 实现阶段以 ORM 注解或 DDL 直接落地                                |
| 本系统对外接口 / 外部接口                 | 框架外（明确排除）    | 本系统当前无外部系统交互                                          |
| 账号体系（登录、认证、人员与角色绑定）            | 框架外（由技术底座提供） | M5 只定义角色与权限的对应关系，不定义账号与认证                             |
| 流程引擎自身能力（流程设计、参与者配置、实例推进、任务查询） | 框架外（由技术底座提供） | M4/M6 只定义流程的业务语义与编排结构                                 |
| 性能、容量、可用性、安全基线等 NFR            | 框架外          | 非功能需求规格                                               |
| BI 数仓、自助分析和指标平台                | 明确排除         | M7 不是 BI 指标模型                                         |

## 10.2  覆盖结论

对于合同管理、资产管理、CRM 等采用单体同步部署的中小型业务系统，本框架能够承载软件需求中的核心业务语义：领域对象及聚合边界、原子用例、业务规则、角色权限（含菜单与按钮级）、端到端业务场景与流程编排、审批流程、跨对象同步联动、跨对象查询统计和固定报表，以及界面菜单导航、屏幕结构、界面元素定义与操作入口。

本框架不应被视为一份完整 SRS 的唯一物理载体。完整交付仍应把八个模型与非功能需求、数据迁移、部署运维和测试验收标准组合起来。八个模型完整覆盖"系统做什么、核心业务为何如此运转、用户如何驱动系统、界面长什么样"，配套规格覆盖"达到什么质量目标以及如何部署运行"。

## 10.3  DDD 与同步编排架构体现

- M1 以聚合根、不变性、值对象和聚合间 ID 引用落实 DDD 领域边界；
- M2 把应用能力拆成原子行为，区分命令与查询；
- M2 `syncTriggers` 把跨聚合联动显式建模为同步调用链，保持事务一致性；
- M3 把业务判断从行为中分离，被同步调用、可独立复用与版本管理；
- M4 以业务场景表达端到端业务的阶段与责任，与可执行编排解耦，业务变化不影响流程实现；
- M6 承担显式流程控制，并通过角色、行为、规则及子流程组合业务旅程；
- M7 将跨聚合读模型与写侧聚合解耦，体现 CQRS 式读写职责分离，但不引入独立 BI 数据模型；
- M5 把权限收敛为唯一的权威配置，界面与行为都不再各自定义权限；
- MU 将界面入口与业务行为解耦，操作功能点通过稳定 ID 引用行为，并强制绑定权限。

## 10.4  已知边界

- **UI/UX**：MU 承载菜单导航、屏幕区块、ASCII 布局、界面元素十项属性、初始化规则与界面事件联动；不建模视觉样式、动画、无障碍、主题与终端适配；
- **账号与权限落地**：M5 只定义角色与权限的对应关系；账号、认证、人员与角色绑定由技术底座承载，不在本体层建模；
- **流程引擎**：M4/M6 只定义业务语义与编排结构；流程实例推进、待办任务查询、流程设计器由技术底座承载；
- **数据库映射**：对象到物理表/字段的映射由实现阶段 ORM/DDL 落地，不在本体层建模；
- **接口**：本系统不涉及外部接口，接口契约不建模；如未来需要对接外部系统，可后续补充；
- 不独立建模性能、容量、可靠性、安全合规等可量化质量属性；
- 不定义消息中间件、消息队列或异步消息实现；跨对象协作一律在同一事务边界内同步完成；
- 不定义数据仓库、指标平台、即席分析或可视化仪表盘。

# 第十一章  实施指南与最佳实践

## 11.1  建模顺序推荐

八个模型之间存在依赖，建议按以下顺序建模：

| 阶段 | 建模对象            | 说明                                                                                |
| -- | --------------- | --------------------------------------------------------------------------------- |
| 1  | M1 对象模型         | 识别聚合、属性、关联、内置约束、refRules 和 invariants                                             |
| 2  | M5 主体模型（角色）     | 识别内部角色及职责边界，权限可稍后补齐                                                               |
| 3  | M3 规则模型         | 梳理跨对象、跨行为或需要独立复用的规则                                                               |
| 4  | M2 行为模型         | 定义对象行为、规则调用、syncTriggers 联动及查询行为入口                                                |
| 5  | M7 查询统计与报表模型    | 在 M1 字段和 M2 查询行为稳定后，建立严格一对一查询报表定义                                                 |
| 6  | M6 流程模型         | 定义端到端协同流和审批流的编排：活动节点、网关、分支、子流程调用                                                  |
| 7  | M4 场景模型         | 在 M6 稳定后，以业务场景视角声明业务目标、起止条件、业务阶段与责任角色、结束触发规则，并引用 M6 流程                            |
| 8  | MU UI 模型（菜单与屏幕） | 定义菜单树、屏幕、区块、ASCII 布局、界面元素十项属性与操作功能点，引用 M2 行为                                      |
| 9  | M5 主体模型（权限）     | 按 MU 落定的菜单与操作功能点建立 MENU / SCREEN / ACTION_POINT 权限，按 M2 行为建立 BEHAVIOR 权限，输出权限分配矩阵 |
| 10 | MU UI 模型（反向校验）  | 用权限分配矩阵回填 `permissionRef`，并反向校验行为可追溯性                                             |

> 顺序要点：**M4 在 M6 之后**（M4 引用 M6 流程）；**M5 的权限部分在 MU 之后**（权限目标来自 MU 的菜单与操作功能点），角色部分在 M1 之后即可先行。

## 11.2  模型评审检查清单

### M1 对象模型评审

- [ ] 聚合边界是否清晰？每个聚合根是否代表一个完整的业务概念？
- [ ] 聚合内的子实体是否真的需要与聚合根同生共死？
- [ ] 聚合之间是否通过 ID 引用而非对象引用？
- [ ] 聚合不变性约束是否完整覆盖了业务规则？
- [ ] 必填、唯一、类型、枚举和数据字典约束是否优先使用属性内置字段？
- [ ] 只依赖当前属性值的扩展约束是否放入 refRules？
- [ ] 依赖同一聚合多个属性或子实体的约束是否放入 invariants？
- [ ] 每个需要编号的对象是否声明了编号规则（对象英文缩写 + YYYYMMDD + 4 位流水号）？

### M2 行为模型评审

- [ ] 每个行为是否真正原子化，只操作一个对象？
- [ ] 前置条件是否完整覆盖了行为可执行的业务前提？
- [ ] 后置状态变更是否完整描述了行为的全部副作用？
- [ ] `syncTriggers` 是否只表达跨聚合联动？同聚合内部变化是否未误用 syncTriggers？
- [ ] `syncTriggers` 中的条件判断是否引用了 M3 规则，而非硬编码在行为里？
- [ ] `syncTriggers` 的下游行为是否与 M4 结束触发规则中声明的行为一致？
- [ ] `queryReportRef` 是否只出现在 behaviorType=QUERY 的行为上，且与 M7 双向一致？
- [ ] 每个 `triggerType=USER_ACTION` 的行为是否都声明了 `requiredPermissions`，且能被 MU 操作功能点反向追溯？

### M3 规则模型评审

- [ ] 是否错误包含了可由属性内置字段、refRules 或 invariants 表达的对象内部规则？
- [ ] 每条规则是否至少涉及跨对象、跨行为或独立复用中的一种？
- [ ] 规则表达式是否无副作用（不改变系统状态）？
- [ ] 规则是否仅被行为同步调用，不主动触发任何行为？

### M4 场景模型评审

- [ ] 每条场景是否对应一个明确的业务目标，而不是某个单一功能？
- [ ] `objectRefs` 是否至少涉及两个独立聚合（单对象增删改查不应建立场景）？
- [ ] `startCondition` 与 `endCondition` 是否可判定（而不是"处理完成"这类空话）？
- [ ] 每个 `stageType` 是否与所声明的引用一致（BEHAVIOR_CALL→behaviorRef、FLOW_CALL→flowRef、RULE_EVALUATE→ruleRef）？
- [ ] 每个阶段的 `roleRef` 是否包含在 `actorRefs` 中，且引用了 M5 已存在的角色？
- [ ] 是否存在可循环的阶段（`nextStages` 指向自身或构成回边），并已显式声明？
- [ ] 是否至少有一个阶段 `isTerminal=true`，且从首个阶段可达？
- [ ] `endRules` 是否覆盖正常结束、异常结束与提前结束三类情形？
- [ ] 场景是否未越界定义网关、活动节点、审批结果、权限或界面元素？
- [ ] `flowRefs` 与 `stage.flowRef` 是否引用了 M6 已存在且无循环的流程？

### M5 主体模型评审

- [ ] 是否未残留外部实体或外部接口契约定义？
- [ ] 每个菜单（一级与二级）是否都有对应的 `MENU` 权限，且至少被一个角色授予？
- [ ] 每个操作功能点（按钮）是否都有对应的 `ACTION_POINT` 权限，且至少被一个角色授予？
- [ ] 每个 `triggerType=USER_ACTION` 的行为是否都有对应的 `BEHAVIOR` 权限，并在 M2 中反向声明？
- [ ] `SYSTEM_ROLE` 是否只持有 `BEHAVIOR` 权限，未持有菜单 / 屏幕 / 操作功能点权限？
- [ ] 多角色并集与 `DENY` 优先规则是否已展开核对，每个「菜单 × 角色」「功能点 × 角色」单元格取值是否唯一确定？
- [ ] 权限分配矩阵是否覆盖全部 `MENU` 与 `ACTION_POINT` 权限，无遗漏行？
- [ ] ABAC 条件是否覆盖了数据隔离需求（如按部门隔离）？`dataScope=DEPT` 是否明确了判定字段与"不含下级"口径？
- [ ] 角色继承关系是否符合最小权限原则，且继承链无环？
- [ ] `ACTION_POINT` 权限与对应 `BEHAVIOR` 权限的授权结果是否一致？

### M6 流程模型评审

- [ ] 每条流程是否明确标记为 COLLABORATION 或 APPROVAL？
- [ ] 是否有且仅有一个开始活动，并至少有一个结束活动？
- [ ] USER_TASK 和 APPROVAL_TASK 是否只引用已存在的 M5 roleId？
- [ ] 活动 roleRef 是否同时包含在流程 roleRefs 中？
- [ ] 协同流的业务阶段是否已在 M4 场景模型中定义，且两者阶段划分一致？
- [ ] 协同流调用审批流时是否通过 subFlowRef 引用，而非复制审批活动？
- [ ] 网关是否至少两个分支、最多一个默认分支，且非默认分支存在判断条件？
- [ ] 审批流是否覆盖通过、驳回、退回等真实结果，并声明结束触发规则？
- [ ] 子流程调用图是否无循环？

### M7 查询统计与报表模型评审

- [ ] 每个对象是否仅直接引用 M1 对象/字段及唯一 M2 QUERY 行为？
- [ ] 是否未定义权限、角色、规则或流程引用？
- [ ] 是否有且仅有一个主查询来源，且所有来源别名和 Join 引用均有效？
- [ ] 多个一对多来源同时参与聚合时，是否先按关联键预聚合？
- [ ] REPORT 是否定义固定列、分组/合计及导出格式？

### MU UI 模型评审

- [ ] 是否采用"总体界面 → 一级菜单 → 二级菜单 → 屏幕（区块 + 元素 + 功能点）"层级？
- [ ] 每个一级菜单是否至少包含一个二级菜单？
- [ ] 每个二级菜单是否关联了屏幕并声明了 `permissionRef`？
- [ ] 每个屏幕是否声明了 `panels`、`elements`、`actions`、`objectAccess`、`initRules`、`linkageRules`？
- [ ] `panels[].order` 是否唯一且覆盖全部元素？主从表界面是否区分了「主表区」与「从表：明细对象名」？
- [ ] 每个元素是否逐项声明了十项关键属性（字段项、控件 ID、对应对象属性、控件类型、数据来源类型、数据源、默认值、可编辑、必填、对应行为）？
- [ ] 控件类型是否遵循映射规则（日期→DATEPICKER、枚举/字典→COMBO、对象引用→POPUP_SELECT、派生计算→LABEL + DERIVED）？
- [ ] 每个操作功能点是否都绑定了 `ACTION_POINT` 权限？
- [ ] `frontendOnly=true` 的元素是否都未设操作功能点？
- [ ] 布局是否遵循规则（单表 2 列、主从主表 3 列 + 从表表格、查询条件 3 列 + 结果表格分页、列表维护"工具栏 + 列表 + 弹窗"、审批处理界面只读、报表查询界面含合计行）？
- [ ] 带审批流的功能是否包含"保存草稿"和"提交"两个独立功能点，且分别绑定独立权限？
- [ ] `initRules` 是否覆盖默认值、初始载入数据、上下文带值、只读可编辑判定、按钮可用性？
- [ ] `linkageRules` 是否全部为纯前端语义，且 `VALIDATE_HINT` 类均写明了真实拦截的规则编号？
- [ ] `objectAccess` 是否与 M4 场景涉及本屏幕的阶段对象一致？
- [ ] 是否所有 USER_ACTION 行为都能从某操作功能点反向追溯？

## 11.3  文件存储、导入与版本管理

模型文件统一位于 `yaml/` 目录：

```
yaml/
├── m1-object-model.yaml
├── m2-behavior-model.yaml
├── m3-rule-model.yaml
├── m4-scenario-model.yaml
├── m5-actor-model.yaml
```

**版本管理约定**：

- 规则模型、场景模型与流程模型支持独立版本；
- `manifest.json` 为可选文件，缺失时按固定文件名识别。

# 附录  术语对照表

| 术语                          | 定义                                                            |
| --------------------------- | ------------------------------------------------------------- |
| 本体（Ontology）                | 对某个领域中概念及其关系的形式化表达                                            |
| 聚合（Aggregate）               | DDD 中的核心概念，是业务完整性的边界，由聚合根、子实体和值对象组成                           |
| 聚合根（Aggregate Root）         | 聚合的唯一入口，负责维护聚合内的业务不变性                                         |
| 子实体（Entity）                 | 聚合内部有标识的对象，依赖聚合根生命周期                                          |
| 值对象（Value Object）           | 无标识的不可变对象，通过属性值判断相等性                                          |
| 聚合不变性（Invariant）            | 聚合内必须始终满足的业务规则                                                |
| 原子行为（Atomic Behavior）       | 不可再分的最小行为单元，只操作单一对象                                           |
| 同步联动（SyncTrigger）           | 行为成功后同步调用下游行为的跨对象联动声明，条件判断可引用 M3 规则                           |
| 场景（Scenario）                | M4 中一条端到端业务从开始条件到结束条件的完整过程，由业务阶段组成                            |
| 业务阶段（Scenario Stage）        | 场景中的一个业务环节：一次明确的业务活动、一个执行角色、一批操作对象                            |
| 结束触发规则（End Rule）            | 流程走到最后一个环节结束后，系统应执行的规则判定、行为调用与记录写入；按正常结束 / 异常结束 / 提前结束三类声明    |
| 端到端协同流（Collaboration Flow）  | M6 中跨业务阶段从开始到结束的完整业务流程的可执行编排                                  |
| 审批流（Approval Flow）          | M6 中由角色承担审批任务，并显式描述通过、驳回、退回及条件网关的流程                           |
| 人工任务（Human Task）            | 由 M5 角色承担的 USER_TASK 或 APPROVAL_TASK                          |
| 子流程（Sub Flow）               | 被另一条 M6 流程通过 subFlowRef 调用的独立流程定义                             |
| 查询报表对象（Query Report Object） | M7 中定义跨对象查询、统计分析或固定报表业务语义的对象，与一个 M2 QUERY 行为严格一对一             |
| RBAC                        | 基于角色的访问控制                                                     |
| ABAC                        | 基于属性的访问控制，比 RBAC 更细粒度                                         |
| 权限目标类型（Target Type）         | M5 权限的控制对象类别：MENU / SCREEN / ACTION_POINT / BEHAVIOR / ENTITY |
| 权限分配矩阵                      | M5 中「权限目标 × 角色」的授权结果表，是角色配置的唯一权威输入                            |
| 数据字典（Data Dictionary）       | 对象模型中的引用数据定义，业务数据保存 code、界面显示 label                           |
| 跳选框（Popup Select）           | 对象引用（AggregateRootRef）的界面控件：左边文本框 + 右边按钮弹出对话框选择               |
| 界面区块（Panel）                 | 屏幕内的版面分区，用于把界面元素按视觉位置与业务用途分组                                  |
| 界面元素（Element）               | 屏幕内可呈现、可操作的最小单位，逐项声明十项关键属性，是界面与对象属性的唯一映射点                     |
| 操作功能点（Action Point）         | MU 中界面上一个按钮/动作到 M2 行为的对应入口，必须绑定一个 ACTION_POINT 权限             |
| 界面事件联动（Linkage Rule）        | 屏幕内由字段变化触发的前端计算、提示与显隐规则，不改变任何对象状态                             |
| 数据来源类型（Source Type）         | 界面元素取数的方式：用户输入 / 系统生成 / 数据字典 / 对象引用 / 派生计算 / 报表对象 / 上下文       |
| 悬空引用（Dangling Reference）    | 模型中引用了不存在的目标，需通过校验防止                                          |
